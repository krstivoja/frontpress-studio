# 69 — General improvement (production asset & perf hardening)

Tracking issue: https://github.com/krstivoja/frontpress-studio/issues/69
(A duplicate #87 was opened then closed in favor of #69.)

Plan for the four valid perf items surfaced by external feedback.
Assessed against the live site (`https://frontpress.studio`), not taken on faith.
Verdict up front: four are legitimate, standard web-perf hygiene and all doable in FrontPress; the fifth ("hashed filenames because names are exposed") is FUD and is not pursued.

Prerequisite already shipped in **1.7.1**: `asset_url()` fingerprints `.css`/`.js` with `?v=<mtime>`.
That is what makes item 1 safe — versioned URLs can be cached forever.

## 1. Long, immutable cache for fingerprinted assets — DONE (1.7.1)

Shipped: `.htaccess` `mod_headers` block (css/js immutable 1yr, fonts 1yr, images 30d); `production.md` documents it + nginx equivalent + Cloudflare "respect existing headers"; changelog bullet added.
Verify after deploy: `curl -sI https://frontpress.studio/assets/style.css?x=1 | grep -i cache-control` → `max-age=31536000, immutable`.
Note: local (`localhost:8081`, nginx via Local) ignores `.htaccess`; only Apache prod reflects it.


**Why.** Assets currently return `Cache-Control: max-age=14400` (4h) — a deliberate compromise from when URLs were unversioned (stale-CSS risk).
Now that css/js carry `?v=<mtime>`, a new build is a new URL, so the old URL can be cached indefinitely with no staleness.

**What.** Serve immutable long-cache headers for static asset types.
This is web-server config, not PHP — it ships as a documented `.htaccess` / nginx snippet, not framework code.

Apache (`.htaccess`, guard with `mod_headers`):

```apache
<IfModule mod_headers.c>
  <FilesMatch "\.(css|js|woff2|woff|ttf|webp|avif|png|jpg|jpeg|gif|svg|ico)$">
    Header set Cache-Control "public, max-age=31536000, immutable"
  </FilesMatch>
</IfModule>
```

nginx:

```nginx
location ~* \.(css|js|woff2?|ttf|webp|avif|png|jpe?g|gif|svg|ico)$ {
  add_header Cache-Control "public, max-age=31536000, immutable";
}
```

**Caveat.** Fonts/images are NOT fingerprinted (by design — relative `url()` inside CSS must keep matching).
So a *replaced* image at the same filename could serve stale for up to a year.
Mitigation: rename an image on meaningful change, or accept it for content images (rare churn).
Document this tradeoff next to the snippet.

**Effort.** Small. Docs + config only.
**Files.** `site/content/docs/production.md` (caching section), plus the shipped `.htaccess` sample if one exists in the repo.

## 2. width/height on Markdown content images — ALREADY DONE (no action)

Discovered `cms/lib/ImageAnnotator.php` already implements exactly this, and it's live (media doc renders `<img … width="1200" height="574">`).
Injects width/height + lazy/async into `/uploads/` images via `getimagesize()`, cached at parse time (runs on edit, not per request), skips images with authored dims, and skips `loading="lazy"` on the first (LCP) image.
Nothing to build. The plan below was written before finding this class — kept for the record but superseded.

---
### (superseded original plan)

**Why.** Homepage `<img>` already carry `width`/`height`/`loading`/`decoding` (verified live) — no CLS there.
The gap is **Markdown body images** (`![alt](x.webp)`), which render without dimensions → layout shift.

**What.** In the Markdown → HTML image rendering path, resolve the image's intrinsic size at render time and inject `width`/`height`.

**Approach.**
- Find the Markdown renderer's image handling (likely a custom renderer/extension around the Markdown parser in `cms/lib/`).
- For local assets (under uploads/theme assets), resolve the file path and call `getimagesize()` (cache the result — content is on disk, cheap but avoid repeat stats within a request).
- Emit `width`/`height` attributes; add `loading="lazy" decoding="async"` for consistency with theme images.
- Skip remote URLs (`http(s)://`) and SVGs (no intrinsic px) — leave those untouched.
- Respect an author who already set dimensions via raw HTML `<img>` (don't double-inject).

**Risks.**
- `getimagesize()` on a missing/broken file returns false — fall back to no attributes, never fatal.
- Path resolution must handle uploads vs theme-asset vs content-relative image URLs correctly.

**Effort.** Medium.
**Files.** Markdown renderer under `cms/lib/` (identify exact class first), tests, docs mention.
**Docs.** Note the auto-dimension behavior in the content/images doc.

## 3. Forced-reflow audit of theme JS — FIX APPLIED (verify with real trace)

Audited all frontpress-v2 theme scripts. Clean: docs-toc.js (IntersectionObserver), dropdown.js, mobile-nav.js, version.js, video.js (no layout reads), fx.js, roadmap.js (classList in handlers, no interleave).
One genuine forced-reflow pattern: **built-with.js** (showcase page) — `cards.forEach` read `frame.clientWidth/Height` then write `card.style.setProperty` synchronously per card → read-after-write interleave → N-1 forced reflows for cached images.
Fix: deferred the write phase into `requestAnimationFrame`, keeping reads synchronous/batched. Node `--check` clean.
Caveat: PSI trace not run in this env — if PSI flagged a different page, get its "Avoid forced reflows" stack to confirm. built-with.js is the only interleaved read/write in the codebase, so it's the clear culprit.
Scope note: theme JS in the marketing checkout, not framework — no framework changelog entry.

---
### (original plan)

**Why.** PageSpeed flags layout thrashing (read layout prop → write → read again in a loop).
This is **theme JavaScript**, not framework — and framework-agnostic (Astro would thrash too if the JS is written this way).

**What.** Audit the theme scripts for interleaved layout reads/writes and batch them (all reads, then all writes; wrap writes in `requestAnimationFrame`).

**Where to look** (frontpress-v2 theme `assets/`):
`dropdown.js`, `mobile-nav.js`, `roadmap.js`, `docs-toc.js`, `video.js`, `fx.js`.
Grep for `offsetWidth`, `offsetHeight`, `offsetTop`, `getBoundingClientRect`, `clientHeight`, `scrollHeight`, `getComputedStyle` used inside loops or immediately after style/DOM writes.

**Approach.**
- Reproduce: run PSI / Chrome DevTools Performance on the live (or local) home + a docs page, capture the "Forced reflow" entries and their JS stack → identifies the exact offending script/line.
- Fix only what the trace actually flags (don't speculatively rewrite clean code).
- Re-measure to confirm the warning clears.

**Effort.** Small–medium, depends on trace.
**Files.** Theme JS in the marketing checkout (`site/themes/frontpress-v2/assets/*.js`) — this is the site, not the framework repo.
Note: this belongs in the marketing-site checkout, not `frontpress-studio`.

## 4. Optional production minify — PARKED (won't do)

Reality check: `ScssCompiler` already defaults to `OutputStyle::COMPRESSED`, so SCSS themes ship minified. The framework already does this.
frontpress-v2 is unminified only because it hand-authors plain `.css` (no `.scss`) — the compiler never touches it.
Converting works (proven: style.css 58KB→46KB, tokens 4KB→2.7KB, compiles clean, selectors/fonts intact) but ROI is low: brotli already compresses the unminified file on the wire (~5% real saving), and it shifts the theme's DX from hand-editing `.css` to editing `.scss`.
Decision (user): park it. Not worth restructuring the live theme.

---
### (original plan)

**Why.** Live `style.css` is unminified (verified: 1138 lines, 58 comment blocks).
Minify saves bytes.
But mandatory build tooling would break FrontPress's core no-build DX — so this must be **opt-in**.

**What.** Add an optional comment-strip + minify pass to the SCSS/CSS compile step, gated by config, **off by default**.

**Approach.**
- `ScssCompiler` already compiles SCSS → CSS; add a post-process minify step.
- Gate behind a config flag (e.g. `assets.minify: true` in `site/config.json`) and/or only when `APP_ENV=prod`.
- Prefer a lightweight, dependency-free CSS minifier (strip comments + collapse whitespace) over pulling a heavy package — keep the no-build spirit.
- JS minify is out of scope for a first pass (theme JS is hand-authored, small) unless trivially bundled.

**Risks.**
- Naive regex minify can corrupt CSS (e.g. inside `content:` strings, `url()`) — use a real CSS-aware pass or a well-tested minifier, plus a test that round-trips known-tricky CSS.
- Must not run in dev (kills readability / live-reload DX).

**Effort.** Medium.
**Files.** `cms/lib/ScssCompiler.php` (+ new minifier helper per the 300-line rule — a flat `cms/lib/` module, not a private method), tests, config doc, changelog.

## Rejected: hashed filenames "because names are exposed"

Exposed asset filenames are not a security issue — every site serves `style.css` at a visible URL.
The real technique underneath (content-hashed filenames) is a marginal caching improvement over `?v=mtime`, but requires a build manifest → conflicts with the no-build model.
`?v=<mtime>` already delivers correct cache-busting with zero build. Not pursued.
